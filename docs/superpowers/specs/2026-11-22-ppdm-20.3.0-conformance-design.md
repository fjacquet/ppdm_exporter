# PPDM 20.3.0 conformance — design (phase 1)

## Intent
Dell shipped 20.3.0 specs (vendored in `docs/swagger/2120*-20.3.0.json`). Know what, if
anything, breaks in the exporter, and make the next spec bump a test failure, not a manual review.

## Findings so far (spec diff 20.1.0 → 20.3.0)
- No path, schema, field, or type removed/renamed on resources we read (additive only).
- New enum values only: `dataMoverType`/`backupMechanism` `UTS`, `backupStrategy`
  `BACKUP_CUSTOM`, asset subtypes (`*_UNIFIED`, `acfs`, `ocfs`, `ocfs2`, `vxfs`),
  `ActivitySubcategory` `FLAT_FILE`/`REBOOT`. Go code never switches on these; values flow to labels.
- Still unchecked: hard-coded enum values in Grafana dashboards/alert rules; whether our
  structs match the specs field-by-field (ADR-0010 fixes appear applied, e.g. `health-results`).

## Goals
- A Go test that checks every `json` tag of the collector structs against the vendored
  spec of the endpoint it decodes: field exists in the response item schema, JSON kind
  compatible (string/number/boolean/array/object).
- Fix real mismatches it reports (struct + fixture, one file each, per ADR-0009).
- ADR-0016 recording the 20.3.0 validation and the new enums.

## Non-goals
- No new metrics, no dashboard changes (phase 2, separate design).
- No generated clients; no change to `ppdmclient`.
- Report-binary DTOs (`internal/report`) are out of this phase unless the test covers them for free.

## Approaches
1. Manual struct-by-struct review (ADR-0010 style): no lasting guard.
2. **Chosen — conformance test.** Table-driven, in `package ppdm`: `{Go type, spec file,
   path, response item schema}`; reflect over struct tags, resolve `$ref`/`allOf`, compare.
3. Hybrid with throwaway script: rejected by the user in favour of 2.

## Constraints
- TDD; `make ci` green; no inline lint suppressions.
- Test skips nothing and needs no network: specs are in-repo.
- Specs are large (1.5 MB): load once per test run.

## Left to the builder
- Registry shape and where it lives (one table in `internal/ppdm/spec_conformance_test.go`).
- How strict on kind compatibility (e.g. integer vs number) — be lenient, flag only real conflicts.
- Dashboard/alert-rule grep for hard-coded enum values: report in the ADR; fix only if a value
  clearly drops data (e.g. a `backupMechanism="VADP"` filter that should also match `UTS`).
